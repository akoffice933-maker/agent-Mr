## 1. Цель продукта

Создать единого AI-агента, управляющего рекламой и продвижением одновременно на трёх платформах:

- **Google Ads**
- **Яндекс.Директ**
- **Авито** (реклама и продвижение объявлений)

Агент работает через естественный язык (RU/EN), имеет единый интерфейс, общую систему безопасности и сквозную отчётность. Основной интерфейс — веб-приложение (чат + панели управления); Telegram-бот и MCP-сервер подключаются позже как внешние клиенты к тому же REST API, не дублируя логику.

### 1.1 Целевая аудитория продукта
- Digital-агентства, ведущие клиентов сразу на нескольких площадках
- In-house маркетологи компаний с несколькими рекламными каналами
- Фрилансеры/подрядчики, обслуживающие несколько кабинетов одновременно

### 1.2 Ключевая ценность
- Единая точка входа вместо переключения между тремя личными кабинетами
- Сводная аналитика и сравнение эффективности каналов
- Защита от случайных трат за счёт единого safety-слоя

## 2. Интеграции с рекламными платформами (реальные API)

Вместо форков трёх GitHub-репозиториев продукт интегрируется напрямую с официальными API площадок. Каждая интеграция инкапсулируется в отдельном адаптере (`src/lib/adapters/<platform>`), который умеет либо ходить в реальный API, либо в mock/seed-режиме отдавать тестовые данные (для dev/demo без боевых ключей).

| Платформа | API | Авторизация | Заметки |
|---|---|---|---|
| Google Ads | Google Ads API (REST/gRPC, `google-ads-api` npm-пакет) | OAuth2 + Developer Token + `customer_id` | Официальный, стабильный, есть sandbox-аккаунты (test accounts) |
| Яндекс.Директ | Яндекс.Директ API v5 + Яндекс.Метрика API | OAuth-токен Яндекса | Требует одобрения приложения Яндексом для прод-объёма запросов; есть песочница (sandbox) |
| Авито | Avito API для бизнеса (Avito.Business API: автозагрузка, статистика, продвижение) | Client ID/Secret (OAuth2) | Официальный набор методов уже, чем 148 tools из avito-mcp — доступ и лимиты уточняются партнёрским соглашением с Авито (см. раздел 13, риски) |

`avito-mcp`, `google-ads-api-agent`, `yadirect-agent` из v1.0 ТЗ остаются как **справочные материалы** (полезны для понимания структуры запросов/ответов конкретных API), но не являются зависимостями продукта — все вызовы реализуются напрямую через официальные клиенты.

### 2.1 Режимы работы адаптера
- **sandbox** — тестовый/песочный контур платформы (где поддерживается) или локальный mock с детерминированными данными
- **production** — реальный кабинет пользователя, требует сохранённых OAuth-токенов

Переключение режима — на уровне записи в `accounts.mode` (уже заложено в текущей схеме БД).

### 4.1 Слой данных
```
┌───────────────────────────────────────────┐
│              PostgreSQL (Drizzle ORM)      │
│   - accounts, campaigns, metrics_daily     │
│   - keywords, negative_keywords            │
│   - avito_chats, recommendations           │
│   - audit_log, pending_actions, settings   │
│   - chat_messages                          │
└───────────────────────────────────────────┘
```
Схема соответствует уже реализованной в прототипе (`src/db/schema.ts`); дополнительно потребуется таблица `oauth_tokens` для хранения токенов реальных интеграций (см. раздел 6.1).

### 4.2 Поток обработки команды
1. Пользователь отправляет запрос на естественном языке (веб-чат / Telegram / MCP-клиент) → `POST /api/agent/chat`.
2. AI Core (OpenRouter, LLM с tool calling) разбирает намерение и выбирает нужные unified-команды — заменяет текущий regex-парсер (`router.ts`) на реальный LLM-вызов с function calling.
3. Unified Tool Layer определяет, на каких платформах нужно выполнить действие, и маршрутизирует вызовы в соответствующие адаптеры.
4. Safety Layer проверяет действие на соответствие политике (лимиты, dry-run, подтверждение) — уже реализовано в `safety.ts`.
5. Адаптер выполняет вызов к реальному API платформы (или возвращает dry-run предпросмотр без записи).
6. Результат агрегируется, логируется в `audit_log` и возвращается пользователю в человекочитаемом виде.

### 4.3 Core Agent как единый маркетинговый ассистент

Ключевой принцип продукта: это **один маркетинговый агент**, а не три отдельных бота под общим UI.

- **Единая память диалога (Session Context)** — агент удерживает контекст между репликами и платформами. Пример: «подними ставки как в Google» после обсуждения Директа должно быть понято как перенос той же логики на другую платформу. Реализуется модулем `src/lib/agent/session-context.ts`, который передаёт последние N сообщений и упомянутые сущности (кампании, площадки, метрики) в промпт LLM при каждом вызове — на сегодня в прототипе история пишется в БД (`chat_messages`), но не передаётся в парсер намерений, это следующий шаг.

- **Кросс-платформенные рекомендации** — агент не просто выполняет команды по каждой площадке отдельно, а умеет предлагать решения на стыке площадок: «CPA на Авито выше, чем в Google — предлагаю снизить бюджет на Авито на 15% и перенести на Google». Модуль `src/lib/agent/cross-platform-advisor.ts`, надстройка над уже существующей генерацией рекомендаций в `tools.ts`.

- **Единая персона и терминология** — один system prompt (`src/lib/agent/prompts/system.ts`), который знает специфику всех трёх площадок и сопоставляет разную терминологию (например, «минус-фразы» в Директе = «negative keywords» в Google Ads).

- **Единый онбординг** — пользователь подключает все три кабинета через общий флоу OAuth (`/settings` → «Подключить площадку»), а не настраивает три инструмента по отдельности.

- **Единая точка политики безопасности** — лимиты бюджета, dry-run и подтверждения задаются один раз на уровне пользователя/аккаунта (уже реализовано в `settings`), а не дублируются по платформам.

## 7. Unified Tool Layer — единые команды

Формат: `имя_инструмента(параметры) -> результат`. Каждый инструмент маршрутизируется в один, несколько или все три адаптера в зависимости от параметра `platforms`. Соответствует реализованному в `src/lib/agent/tools.ts`.

| Команда | Назначение | Платформы |
|---|---|---|
| `get_spend_report(date_from, date_to, platforms)` | Сводный расход за период | Google, Директ, Авито |
| `compare_cpa(date_from, date_to, platforms)` | Сравнение CPA между площадками | Google, Директ |
| `pause_low_ctr_campaigns(threshold, platforms)` | Пауза кампаний с CTR ниже порога | Google, Директ |
| `promote_low_view_listings(platform="avito")` | Продвижение объявлений с низким охватом | Авито |
| `run_account_audit(platforms)` | Аудит подключённых кабинетов | Google, Директ, Авито |
| `adjust_bids(percent, filter, platforms)` | Изменение ставок по фильтру | Google, Директ |
| `create_campaign(spec, platform)` | Создание кампании | Google, Директ, Авито |
| `list_campaigns(platform, status)` | Список кампаний с фильтром по статусу | Google, Директ, Авито |
| `get_keyword_performance(campaign_id, platform)` | Статистика по ключевым словам | Google, Директ |
| `add_negative_keywords(campaign_id, keywords, platform)` | Добавление минус-фраз | Google, Директ |
| `get_avito_chat_summary(period)` | Сводка по чатам/лидам Авито | Авито |
| `list_recommendations()` / `apply_recommendation(id)` | Список и применение рекомендаций | Google, Директ, Авито |

### 7.1 Примеры естественноязыковых команд
- «Покажи расходы по Google, Директу и Авито за последние 7 дней»
- «Поставь на паузу кампании с CTR ниже 1%»
- «Продвинь объявления на Авито с низким количеством просмотров»
- «Сравни CPA между Google Ads и Яндекс.Директ»

## 9. User Stories

**US-1.** Как маркетолог агентства, я хочу одной командой получить расход по трём площадкам за неделю, чтобы не заходить в три кабинета отдельно.
*Критерий приёмки:* команда `get_spend_report` возвращает таблицу с разбивкой по платформам и итогом, ответ формируется < 15 сек.

**US-2.** Как владелец рекламного бюджета, я хочу, чтобы система запрашивала подтверждение перед изменением бюджета, чтобы избежать случайных трат.
*Критерий приёмки:* любое действие, влияющее на бюджет, при выключенном dry-run требует явного подтверждения (`pending_actions`) перед выполнением. *(реализовано в прототипе)*

**US-3.** Как менеджер по продажам на Авито, я хочу автоматически продвигать объявления с низким числом просмотров, чтобы увеличить поток лидов без ручной рутины.
*Критерий приёмки:* `promote_low_view_listings` находит объявления ниже порога просмотров и предлагает/выполняет продвижение через реальный Avito API (или dry-run предпросмотр).

**US-4.** Как аналитик, я хочу сравнить CPA между Google Ads и Яндекс.Директ за произвольный период, чтобы перераспределить бюджет в пользу более эффективного канала.
*Критерий приёмки:* `compare_cpa` возвращает CPA по каждой платформе и % разницы.

**US-5.** Как оператор, я хочу видеть полный audit-log всех действий агента, чтобы иметь возможность расследовать инцидент или откатить изменение.
*Критерий приёмки:* каждое действие (включая dry-run) пишется в `audit_log` с timestamp, инициатором, параметрами и результатом. *(реализовано в прототипе)*

**US-6.** Как пользователь Telegram, я хочу управлять кампаниями текстовыми сообщениями, чтобы делать это с телефона без веб-интерфейса.
*Критерий приёмки:* Telegram-бот (`telegram-bot/`) вызывает `/api/agent/chat` и получает тот же результат и тот же уровень подтверждений, что и веб-чат.

**US-7.** Как разработчик, интегрирующий стороннего AI-агента, я хочу подключиться через MCP, чтобы использовать unified-команды из своего инструмента.
*Критерий приёмки:* MCP-сервер (`mcp-server/`) публикует unified-команды как MCP tools с валидной JSON Schema, проксируя вызовы в тот же REST API.

**US-8.** Как маркетолог, я хочу, чтобы агент сам предлагал перераспределение бюджета между площадками на основе сравнения эффективности, а не только выполнял мои прямые команды.
*Критерий приёмки:* после запроса сводной аналитики агент (`cross-platform-advisor.ts`) формирует минимум одну рекомендацию по переносу бюджета между платформами, если разница в CPA/CTR превышает заданный порог, и предлагает её на подтверждение.

**US-9.** Как пользователь, я хочу, чтобы агент помнил контекст предыдущих реплик в рамках диалога, чтобы не повторять названия кампаний и площадок каждый раз.
*Критерий приёмки:* при ссылке на «ту же кампанию» или «как в Google» агент корректно подставляет последнюю упомянутую сущность из `session-context.ts` (передаётся в промпт LLM).

## 10. Требования к безопасности

- Dry-run режим включён по умолчанию для всех операций записи
- Обязательное подтверждение всех действий, влияющих на бюджет
- Лимиты расходов: дневной / недельный / месячный, настраиваемые по аккаунту
- Полный audit-log (кто, что, когда, с какими параметрами, результат)
- Режим «только чтение» для аналитических/гостевых пользователей
- Поддержка тестовых/песочных режимов платформ (где доступно) и локального seed-fallback при отсутствии токенов
- Хранение OAuth-токенов и API-ключей в БД в зашифрованном виде (`oauth_tokens`, шифрование на уровне приложения) или в секрет-менеджере, не в коде и не в открытом виде

*(Разделы про dry-run, лимиты, pending_actions, audit-log уже реализованы в прототипе — `src/lib/agent/safety.ts`.)*

## 12. Критерии готовности MVP

- Управление Google Ads, Яндекс.Директ и Авито из одного веб-интерфейса, подключёнными через реальные OAuth-интеграции (не только seed-данные)
- AI Core работает через LLM с tool calling (OpenRouter), а не через rule-based парсер
- Работают Web App, MCP-сервер и Telegram-бот как единый REST API с тремя клиентами
- Есть защита от случайных трат (dry-run, лимиты, подтверждения) — уже выполнено в прототипе
- Есть базовая сводная аналитика, аудит и кросс-платформенные рекомендации по трём платформам
- Все действия логируются в audit-log — уже выполнено в прототипе

## 13. Открытые вопросы

- **Доступ к Avito API для бизнеса** — уточнить условия партнёрского доступа, лимиты и доступный набор методов (может быть уже официального набора из avito-mcp); это риск для сроков этапа 5.
- Модель хостинга: Vercel + managed Postgres vs self-hosted VPS (Docker Compose) — влияет на деплой `mcp-server/` и `telegram-bot/` как отдельных процессов.
- Мультитенантность: нужна ли поддержка нескольких клиентов/агентств в одном инстансе с изоляцией данных.
- Биллинг использования LLM (OpenRouter) при высокой частоте запросов — нужен ли контроль расходов на сам AI-слой.
- Хранение и ротация OAuth-токенов трёх площадок — единый секрет-менеджер или шифрование на уровне БД.
