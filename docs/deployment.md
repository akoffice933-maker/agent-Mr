# Развёртывание в продакшене

Пошаговый порядок вывода Unified AI Ads Agent в боевую эксплуатацию.
Каждый шаг заканчивается проверкой: если проверка не проходит, дальше
идти нельзя.

Docker-образ, `docker-compose.yml` и healthcheck-роут уже есть в
репозитории — этот документ описывает, что нужно **сделать вокруг них**.

---

## 0. Что уже готово, а что требует решения

| Готово | Требует вашего участия |
|---|---|
| `Dockerfile` (standalone, non-root, миграции при старте) | Хостинг и домен |
| `docker-compose.yml` (Postgres + app + профиль `clients`) | TLS-сертификат и reverse-proxy |
| `GET /api/health` (503 при недоступной БД) | SMTP для писем |
| RLS FORCE на 13 таблицах, `npm run audit:rls` | OAuth-приложения площадок |
| Rate limiting, brute-force защита, AES-256-GCM | Redis, если реплик больше одной |

## 1. Секреты

Сгенерируйте значения, а не придумывайте:

```bash
openssl rand -base64 32   # ENCRYPTION_KEY
openssl rand -hex 32      # AGENT_API_KEY
```

`ENCRYPTION_KEY` шифрует OAuth-токены площадок в базе.

> **Его потеря необратима.** Расшифровать сохранённые токены будет
> нечем: все подключённые кабинеты придётся подключать заново.
> Храните копию отдельно от сервера — в менеджере секретов, а не
> в `.env` рядом с приложением.

Смена ключа на живой базе не поддерживается автоматически: старые
токены после неё не расшифруются.

**Проверка:** в `.env` нет ни одного значения из `.env.example`
(`change-me…`, `apppass`).

## 2. База данных

Роль приложения обязана быть **подчинена RLS** — это несущая часть
изоляции клиентов.

```sql
CREATE ROLE appuser LOGIN PASSWORD '<сильный пароль>';
-- НЕ давайте SUPERUSER и НЕ давайте BYPASSRLS.
```

Владелец схемы и миграции — отдельная привилегированная роль. Приложение
работает под `appuser`.

```bash
DATABASE_URL=postgresql://appuser:...@host/app_db npm run migrate
DATABASE_URL=postgresql://appuser:...@host/app_db npm run audit:rls
```

> Миграции применяются автоматически при старте контейнера
> (`CMD` в `Dockerfile`), поэтому отдельный шаг нужен только при
> ручном развёртывании.

**Проверка:** `npm run audit:rls` печатает `RLS FORCED: 13 tables` и
завершается кодом 0.

> `npm run migrate` печатает `MIGRATE OK` даже когда фактически ничего
> не применил: порядок берётся из поля `when` в
> `drizzle/meta/_journal.json`, и миграция с меньшим `when`
> пропускается молча. После деплоя убеждайтесь в наличии новых
> таблиц/индексов по самой схеме, а не по этому сообщению.

## 3. Обязательные переменные окружения

| Переменная | Значение | Почему важно |
|---|---|---|
| `DATABASE_URL` | роль без BYPASSRLS | изоляция клиентов |
| `ENCRYPTION_KEY` | 32+ случайных байта | шифрование токенов |
| `AGENT_MODE` | `production` | fail-closed: без `AGENT_API_KEY` REST API отдаёт 503 |
| `AGENT_API_KEY` | случайный ключ | доступ MCP/Telegram-клиентов |
| `APP_BASE_URL` | `https://ваш-домен` | ссылки в письмах |
| `PUBLIC_URL` | `https://ваш-домен` | OAuth redirect-uri |

`APP_BASE_URL` **никогда** не выводится из заголовка `Host`: подделанный
заголовок отправил бы ссылку подтверждения на чужой домен — это готовый
захват аккаунта.

Полный список с пояснениями — в `.env.example`. Тест
`tests/unit/env-documented.test.ts` следит, чтобы файл не отставал от кода.

## 4. Reverse-proxy и TLS

Приложение слушает HTTP; TLS терминирует прокси.

```nginx
proxy_set_header X-Forwarded-For "$remote_addr, $server_addr";
```

> Именно так, а не `$proxy_add_x_forwarded_for`. Код доверяет
> **последнему** хопу и требует минимум двух. С одним хопом доверие не
> сработает никогда, и все клиенты попадут в общий бакет `untrusted` —
> один посетитель сможет исчерпать лимит и локаут для всех остальных.
> Добавлять заголовок к присланному клиентом тоже нельзя: клиент
> подставит фальшивые хопы перед настоящим.

`TRUSTED_PROXY` — адрес или CIDR самого прокси.

**Проверка:** с двух разных адресов лимиты расходуются независимо.

## 5. Масштабирование

Одна реплика работает без Redis. **Две и больше — только с ним:**

```
REDIS_URL=redis://:password@redis:6379/0
```

Без Redis счётчики лимитов лежат в памяти процесса. Тогда:

- фактический лимит умножается на число реплик;
- локаут после пяти неудачных входов обходится переподключением
  к другой реплике;
- счётчики обнуляются при каждом деплое.

Если `REDIS_URL` указан, но Redis недоступен, приложение не падает —
оно переключается на память (fail-open). Сервис остаётся жив, но
ограничения снова становятся «на реплику», причём молча. Заведите
отдельный мониторинг доступности Redis.

Следите, чтобы `реплики × DB_POOL_MAX` не превышало `max_connections`
Postgres: `withTenant()` держит соединение на весь запрос, а запрос
к агенту может ждать ответа LLM десятки секунд.

## 6. Почта

Без `SMTP_HOST` приложение работает, но ссылки подтверждения и сброса
пароля не отправляются, а пишутся в лог.

Включайте `SIGNUP_REQUIRE_VERIFIED_EMAIL=on` **только после** того, как
убедились, что письма доходят: иначе вход будет закрыт для всех, включая
вас.

**Проверка:** регистрация тестового адреса → письмо получено → ссылка
ведёт на `APP_BASE_URL` → вход выполняется.

## 7. OAuth площадок

Redirect URI в кабинете каждой площадки должен совпадать с
`PUBLIC_URL` **посимвольно**, включая схему и завершающий путь. Яндекс
и Google отклоняют несовпадение целиком.

Проверьте, что в продакшене **не установлен** `YANDEX_SIMULATOR=1`:
с ним запросы к Директу не уходят наружу, а пользователь уверен, что
управляет своими кампаниями.

`IMAGE_FETCH_ALLOWLIST` **сужает** список хостов, откуда разрешено
скачивать картинки. Пустое значение — не запрет: разрешён любой
публичный адрес. От SSRF защищает не он, а безусловная проверка в
`src/lib/net/fetch-safe.ts` — она отклоняет loopback, приватные и
link-local диапазоны (включая `169.254.169.254`, метаданные облака),
а также имена вроде `localhost` и `*.internal`.

Задавайте allowlist, если картинки берутся из известного CDN: это
превращает разрешительную модель в запретительную и закрывает случаи,
до которых проверка диапазонов не дотягивается (например, публичный
редиректор внутрь вашей сети).

## 8. Проверка после деплоя

```bash
curl -fsS https://ваш-домен/api/health        # 200 и {"ok":true,"db":true}
curl -o /dev/null -w '%{http_code}\n' https://ваш-домен/api/agent/chat   # 401/403, не 200
```

- `mode` в ответе `/api/health` — `production`;
- `auth` — `api-key`;
- лендинг `/` открывается без авторизации;
- `/agent`, `/billing`, дашборд — редиректят на вход;
- письма приходят, ссылки ведут на боевой домен.

`/api/health` возвращает **503** при недоступной базе — навешивайте на
него проверку балансировщика и мониторинг.

## 9. Эксплуатация

**Резервные копии.** `pg_dump` по расписанию плюс отдельная копия
`ENCRYPTION_KEY`. Дамп без ключа бесполезен: OAuth-токены в нём
зашифрованы. Регулярно проверяйте восстановление на отдельном стенде —
непроверенной копии не существует.

**Обновление.** Миграции применяются при старте контейнера. Схема
пишется совместимо, но перед выкладкой всё равно снимайте дамп.

**Что смотреть в логах.** `LOG_FORMAT=json` для сборщика. Тревожные
события: `signup.code_mode_without_secret`, всплеск 401/403,
`analytics first-event failed`, ответы 503 от `/api/health`.
